## Dev mode: nothing triggers a recompile when an imported file changes

Date: 2026-07-28. Surfaced by moving file collection into the remark pass,
which closed the half of this problem it could and revealed the other half
cleanly.

**What's fixed.** `remarkPlugin` now re-walks a demo's whole graph on every
MDX compile, so any recompile reflects current disk content for the entry
_and_ everything it imports. `demoDataByRef` and the stale-data warnings are
gone.

**What isn't.** That's a different question from what _causes_ a recompile.
Rspack watches the MDX file and a `file=`'s literal target (core registers
that path), but not a file reached only through `collectDemoFiles`'s own
`readFileSync` — invisible to the bundler's dependency graph. So editing
_only_ a file the entry imports changes nothing on screen until something
else triggers a compile. **Verified against a real dev server across three
trials**, including a `readFileSync`-vs-DOM check to rule out browser
caching; editing the entry afterwards picked up both edits, which is what
proves the walk itself is fresh.

**The unresearched lever**, carried over from the entry this replaces:
whether rspress exposes the webpack/Rspack loader's `addDependency` to remark
plugins. If it does, registering each file `collectDemoFiles` reads would
close this exactly. If it doesn't, the options are worse — a chokidar watcher
owned by the plugin, or accepting it.

**Deliberately not acted on**: the fix is a design decision, not a mechanical
follow-up, and the workarounds are all heavier than the bug. Documented as a
limitation in `packages/rspress/CLAUDE.md` ("Dev-mode staleness: what a
recompile picks up vs. what triggers one").

**Unparked by:** finding out whether `addDependency` is reachable — that one
fact decides between a clean fix and no fix.
