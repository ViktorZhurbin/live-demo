## Dev-mode staleness: collapse the two-parse scan into remark

`routeGenerated` (`visitFilePaths.ts`) still scans every MDX file once per
dev-server process and stashes results in `demoDataByRef`, keyed by
`demoRefKey`; `remarkPlugin.ts` reads them back on every recompile. The
external architecture review's core suggestion — run `collectDemoFiles`
synchronously inside the remark pass instead, keyed off `vfile.path`,
deleting `demoDataByRef`/`demoRefKey`/the `console.warn` fallback entirely —
was not taken.

What _did_ ship since (the "file" meta commit, `4ec06e2`): `remarkPlugin.ts`
now overrides just the entry file's own content with `node.value` on every
recompile, since `@rspress/core`'s `remarkFileCodeBlock` re-reads it from
disk anyway. That closes the single most common case (editing a demo entry
file's own code) without the larger rewrite. Still needing a dev-server
restart: adding/removing one of the entry's own imports, editing a file the
entry merely imports, adding a brand-new demo, and the deprecated
`<code src>` path — all documented in `packages/rspress/CLAUDE.md`'s
"Deliberately not handled" section.

The bigger rewrite's real obstacle, per `docs/ongoing/upstream-plugins-takeaways.md`'s
independent analysis of the same idea: `uniqueImports` feeds the virtual
module, generated once at build-config time — a demo gaining a brand-new
_external_ import mid-session would still need that module regenerated, so
the full fix needs an equivalent to `plugin-preview`'s `isDirtyRef`
dev-server-restart trick, or accepting that smaller residual gap. Whether
rspress exposes the loader's `addDependency` to remark plugins (which would
also fix same-session edits to files an entry merely imports) is still
unresearched.

**Unparked by:** picking up the full architecture change, or deciding the
current partial fix is good enough to stop here.
