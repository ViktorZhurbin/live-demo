## Resolve externals from a CDN when the build-time registry misses

Date: 2026-07-31. Prompted by CodePen 2.0, which ships exactly this.

ADR 0003 lists CDN module resolution as a Ring 3 exploration — the one that
changes the product's ceiling, since it removes `EXTERNAL_IMPORT_NOT_FOUND` and
the whole build-time-discovery constraint. CodePen 2.0 now does it in
production: detect bare specifiers, auto-generate a `package.json`, emit an
**import map**, serve from **esm.sh**, with versions editable in the generated
manifest and an override syntax for transitive pins (`pkg@ver?deps=dep@ver`).

**Their mechanism does not port.** Import maps only bind native ESM `import`.
This runtime transpiles to CommonJS and evaluates through `new Function` with a
synthetic `require` (`moduleRunner.ts`), so the browser's module resolver is
never consulted and an import map would do nothing.

**The seam that does exist is better shaped.** `runCode.ts` already walks every
reachable file, collects `externalImports`, and awaits `loadImports([...])`
before `createModuleRunner` evaluates anything — its docblock explains why that
ordering exists (a freshly-edited import the build step never saw still works).
A CDN fallback for specifiers the build-time registry doesn't know lands in that
prefetch pass, and `requireModule` stays synchronous. So the exploration is
cheaper than the ADR implies: no restructuring, one fallback branch in
`loadImports`, and `EXTERNAL_IMPORT_NOT_FOUND` becomes the "CDN missed too"
error rather than the first error.

Worth knowing before pricing it: even CodePen doesn't get this uniformly —
their limitations page concedes that server-processed files "may not support
bare imports except built-in Block packages."

**Still Ring 3, not unparked.** Ring 2 names "arbitrary npm resolved at
runtime" as out. What CodePen changes is the cost estimate and the existence of
a reference implementation, not the scope verdict. Unparking this is a
deliberate ADR 0003 amendment, not a follow-up.

## `previewLanguages` + `previewCodeTransform` — needs more thought

Upstream `@rspress/plugin-preview` exposes a user-supplied
`({ language, code }) => code` hook at the remark stage plus a configurable
trigger-language list (`.claude/source-code/plugin-preview/docs-api.md`). ~10
lines of plugin surface that lets someone support a language this plugin has
never heard of. `remarkPlugin`, which now does its own file resolution, is the
natural home.

**Why it's still parked.** Upstream's motivating example is a Vue SFC. This
runtime is Sucrase → JS → React, so non-React output can't render regardless of
what the hook returns — ADR 0003's test rules that out as a non-React mount.
What's left is "pre-transform a fence into JS/JSX", which is real and Ring 1,
but has no known consumer.

**What CodePen 2.0 adds to the question.** Their **Blocks** are the same idea
built the other way round, and the two conventions they landed on are the part
worth taking:

- **Dispatch on file extension, not on a plugin option.** A `.scss` file
  triggers the Sass block; there is no `previewLanguages` list to keep in sync
  with reality. Upstream's paired-option design exists because a fence has no
  extension — but `file=` demos do, and multi-file demos are this plugin's
  differentiator.
- **Reuse the tool's native config filename.** `babel.config.json` where a
  standard exists; a namespaced `.codepen/sass.config.json` only where none
  does. Cheaper to learn and cheaper to document than nesting third-party
  config under a plugin option.

That reframes the item: an extension-keyed transform registry is a different and
probably better shape than a language-list-plus-callback, and it converges with
the CSS Modules item below rather than sitting beside it. **Deliberately not
resolved** — the two should be designed together or not at all.

**Unparked by:** either a concrete consumer, or taking the CSS Modules item,
which forces the extension-dispatch decision anyway.

## CSS Modules in demos

Fuller analysis in `./css-imports.md` while that file lasts; the
load-bearing conclusions are here.

No bundler needed and bringing Rollup back would buy nothing. ~100 lines, no
new dependency: rewrite `.foo` selectors to `.foo_<hash>` and return the
class-name map as the module's exports. Ring 1 under ADR 0003. Closes
rspress#1269 / #1394-style bleed in the direction achievable without an iframe —
demo styles stop leaking out; docs leaking in still needs shadow DOM or an
iframe, both Ring 3.

Build **CSS Modules, not plain CSS imports.** A bare `<style>` injection is
global and unscoped — the exact bug upstream's iframe modes exist to escape. The
scoping is the feature and the docs should say so.

Touches the same `collectDemoFiles`/`analyzeModule` path the file-collection
refactor changed: `remarkPlugin` re-walks per compile, so a per-file `<style>`
element has to key off the same `(absolutePath, mtimeMs)` cache. Design the
`<style>` lifecycle up front — with an 800ms debounce, every recompile injects
another node unless keyed, replaced, and removed on unmount.

## Per-block meta options

`website/docs/guide/customization.mdx` says outright there's no per-demo
override — the most obviously-shaped gap. `parseCodeMeta.ts` already tokenizes
every `key=value` pair and discards all but `file`; extending it costs plumbing,
not parsing. Ring 1 under ADR 0003, no further scope argument needed.

Worth carrying: default view (`view=preview` to open on Preview instead of
Split), `direction=vertical`, and hiding the editor or control panel for one
demo. Inline and `file=` demos both already carry meta; don't extend
the deprecated `<code src>`.

Frontmatter as a middle precedence tier (block > frontmatter > plugin chain,
read at runtime via `usePageData()` so it costs nothing at build time) is a
natural follow-on once per-block exists — upstream does exactly this. Split it
out; per-block alone covers the common "hide the editor for this one demo" need.

## Verify `resolve.alias` already covers library self-aliasing

Tiny, and verification comes first. The one capability behind upstream's removed
`includeModules` that survives: a component library's own docs writing
`import { Button } from 'my-lib'` and having it resolve to `../src/index.ts` —
the primary audience for this plugin category, and Ring 1 under ADR 0003.

May already work with zero code. `getVirtualModulesCode.ts` emits
`import('my-lib')` into a virtual module that the consuming bundler resolves, so
a `resolve.alias` entry in the user's own rspress config should apply. Check
that before writing an option. If it works, it's a paragraph in
`customization.mdx`. If not, the minimal version is an alias map applied at
`getVirtualModulesCode` — the specifier still has to be imported by some demo to
land in the map, so the `includeModules` removal rationale stays intact.

## Dev mode: nothing triggers a recompile when an imported file changes

Date: 2026-07-28. Surfaced by moving file collection into the remark pass, which
closed the half of this problem it could and revealed the other half cleanly.

**What's fixed.** `remarkPlugin` now re-walks a demo's whole graph on every MDX
compile, so any recompile reflects current disk content for the entry _and_
everything it imports. `demoDataByRef` and the stale-data warnings are gone.

**What isn't.** That's a different question from what _causes_ a recompile.
Rspack watches the MDX file and a `file=`'s literal target (core registers that
path), but not a file reached only through `collectDemoFiles`'s own
`readFileSync` — invisible to the bundler's dependency graph. So editing _only_
a file the entry imports changes nothing on screen until something else triggers
a compile. **Verified against a real dev server across three trials**, including
a `readFileSync`-vs-DOM check to rule out browser caching; editing the entry
afterwards picked up both edits, which is what proves the walk itself is fresh.

**The unresearched lever:** whether rspress exposes the webpack/Rspack loader's
`addDependency` to remark plugins. If it does, registering each file
`collectDemoFiles` reads would close this exactly. If it doesn't, the options
are worse — a chokidar watcher owned by the plugin, or accepting it.

**Deliberately not acted on**: the fix is a design decision, not a mechanical
follow-up, and the workarounds are all heavier than the bug. Documented as a
limitation in `packages/rspress/CLAUDE.md` ("Dev-mode staleness: what a
recompile picks up vs. what triggers one").

**Unparked by:** finding out whether `addDependency` is reachable — that one
fact decides between a clean fix and no fix.
